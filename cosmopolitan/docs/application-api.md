# Application services and Python replacement

Baseline: `b42704a624652a53099fbc994e9a6b7648cd3b0c`. This document records
the application work that remains around the shared native model engines.
The native C++ UI, HTTP server and command entry points are integration
components; their presence does not establish parity with every existing
Easy Diffusion feature.

## Route inventory

[`api-inventory.json`](api-inventory.json) was generated by
[`inventory_api.py`](../tests/inventory_api.py), which parses source without
importing or starting the Python application. At this baseline it finds:

- 168 literal Python route declarations across the scanned application,
  plugin and training directories.
- Four router mounts, with their prefixes recorded separately.
- 20 literal native route declarations in the existing SDKit server and
  Cosmopolitan UI adapter.
- No Python parse errors in the 128 scanned files.

These are declaration counts, not counts of unique active endpoints or a
percentage of completed work. Legacy and plugin copies declare some of the
same routes. Router prefixes, dynamically registered UI pages, middleware,
plugin discovery and application startup determine the effective interface.
The inventory is an audit input, not a generated OpenAPI schema.

The existing Python server contributes 72 declarations. The training plugin
contributes another 31, covering a much larger lifecycle than a command that
invokes the native trainer. The two model-browser copies each contribute 23,
the two model-tools copies each contribute eight, and the bucket manager
contributes three. The inventory retains file names, handlers and source
locations so an implementer can resolve the active modules before replacing
their behavior.

## Responsibilities to preserve

| Area | Existing sources | Required native behavior and evidence |
| --- | --- | --- |
| Generation | `ui/easydiffusion/server.py`, task modules, native SDKit server | Preserve accepted requests, model and device selection, seeds, outputs, progress, cancellation and error responses; validate an actual checkpoint |
| Jobs and queues | `ui/easydiffusion/task_manager.py`, `ui/easydiffusion/tasks`, training service | Own task state and worker lifetimes, serialize incompatible model mutations, release memory on failure, and retain observable progress/history |
| Training | `training`, `ui/plugins/server/training`, native SD 1.5 trainer | Preserve dataset preparation, configuration validation, launch/stop/status, samples, exports and supported schedules; explicitly reject unavailable training options |
| Model discovery, downloads and conversion | Online model browser and model-tools modules | Preserve model metadata, authenticated-service configuration where used, download and conversion progress, cancellation, resulting file integrity and tokenizer/configuration handling |
| Tagging and vision | Native WD14 and vision tools, application routes | Preserve preprocessing, labels, confidence rules and output formats; resolve ONNX Runtime and LibTorch execution dependencies |
| Galleries, files and configuration | Server, bucket manager, gallery and settings modules | Preserve path handling, metadata, saving, preferences and persistent application state |
| Plugins and online services | `ui/plugins`, `plugins`, native plugin-related code | Define supported plugin APIs and execution mechanisms, settings and error reporting; a bundled script is not automatically a native implementation |
| C++ UI | `source/UI.cpp` and linked scripts/styles | Serve the rendered pages and resources, then connect every control to an implemented service with compatible responses |

The current native server exposes its own generation and configuration
routes. Similar names alone do not prove compatibility with the Python
frontend. Compare methods, request fields and defaults, response bodies,
streaming or polling behavior, status codes and interruption semantics.

The C++ UI renders 16 pages, including training, tagging, datasets, model
downloads, galleries and settings. A rendering check proves that those pages
and their assets are packaged. Many controls still target Python application
APIs. Functional acceptance must exercise the control, its request, the
native operation and the resulting state or file.

## One shared runtime and explicit ownership

One GGML implementation gives llama.cpp, diffusion and the custom trainer a
consistent tensor layout, operation set and backend registry. It does not
automatically coordinate simultaneous requests. The application needs one
job/resource coordinator above those engines.

Each job should hold explicit leases on its model, weight representation,
backend buffers and working memory. Read-only inference jobs may share
compatible immutable weights. A training job needs a deliberate policy for
mutable weights, adapters, gradients and optimizer state. Cancellation must
stop work before those allocations are released; model unloading must wait
for all outstanding users. See the
[Colibri and KoboldCpp review](resource-management.md) for useful existing
ownership and residency patterns.

Memory estimates must include working activations, attention/KV state,
conversion buffers, gradients and optimizer state as appropriate. A model's
file size alone does not establish whether a particular job fits. CPU and
device budgets need separate accounting, especially when offload or a
temporary conversion holds two representations at once.

LibTorch and ONNX Runtime have their own tensor, allocator, execution and
threading contracts. If retained, they must participate in the same resource
policy; their internal allocations cannot simply be treated as GGML tensors.
Any shared-buffer adapter needs compatible layout, type, alignment, lifetime,
synchronization and mutation rules. A C function wrapper alone supplies none
of those guarantees.

The staging patch renames the HTTP file catalog from `ModelManager` to
`SdkitModelIndex`. It leaves the diffusion weight/residency `ModelManager`
intact. These were unrelated C++ classes with the same global name and header
guard. Distinguishing them removes an actual static-link/definition conflict;
both engines and the trainer still use the one authoritative GGML runtime.

## C interfaces and existing C++

New process entry points and llama orchestration use C where practical.
C++ adapters retain the existing renderer, server, diffusion engine and
trainer implementation. Interfaces across that boundary need explicit
ownership, bounded input lengths, result/error values and cancellation or
progress callbacks. C++ exceptions must be caught before returning through a
C entry point.

Replacing a Python caller of LibTorch with a C wrapper does not port ATen,
autograd, serialization, dispatch, threading or device libraries to
Cosmopolitan. The existing native tools must either bring that dependency
closure into the portable build or receive a separately validated native
implementation of their required model behavior.

Likewise, llama.cpp's supported model implementations do not replace all
Transformers processors, tokenizers, model families, conversion logic or
training paths. List the models and workflows the application actually uses,
then test the replacement on those inputs before removing the original
Python implementation. Build-time Python scripts used to prepare this
branch are separate from a deployed Python dependency.

## API terminology and contract work

OpenAPI describes an HTTP interface: schemas, operations, authentication,
responses and errors. OpenAI-compatible endpoints are a particular service
contract that can be described with OpenAPI. Intel oneAPI/SYCL is an
accelerator/toolchain concern. Track them separately when adding the user's
requested APIs.

For each application operation, record its effective route and owner, input
and output schema, defaults, error cases, state transitions, cancellation
rules, resource use and persistence requirements. Then map it to the native
implementation and a functional acceptance case. Do not infer this contract
solely from the route declaration inventory.

## Completion gates

The first combined executable checks model-engine linkage, shared GGML math,
real inference with a small trained llama fixture, existing trainer math,
server startup and embedded UI rendering. Separate gates remain for:

1. Image generation with an actual supported diffusion checkpoint, including
   saved output and interruption behavior.
2. An end-to-end supported SD 1.5 training recipe with dataset loading,
   parameter updates, sampling and export checked independently.
3. Effective application route coverage and functional UI workflows, including
   queue contention and cancellation during model loading or computation.
4. LibTorch, ONNX, conversion, tokenizer/processor and other remaining Python
   replacements.
5. Accelerator-specific inference and backward-operation coverage, device
   loss/error handling and the correct supported fallback.

The build and test reports must identify which gates were actually exercised.
Keep the original application implementations available until their required
behavior is replaced and verified.
